# 裁判系统装甲受击小闭环任务

> 用途：硬件到货后，按本文搭建“四块自制装甲板 + 小裁判主板 + 车端 `modules/REFEREE`”的最小受击闭环。

---

## 目标与边界

目标是实现一个最小裁判系统闭环：

```text
四块自制装甲板
  -> 小裁判主板检测 / 汇总受击事件
  -> 小裁判主板按 RoboMaster 2026 通信协议发送裁判串口帧
  -> 车端 USART6 / modules/REFEREE 接收解析
  -> 车端获得血量 / 受击 / 比赛状态等数据
```

本阶段只做“装甲受击 + 串口裁判数据下发”的小闭环，不做完整官方裁判系统。

边界：

1. 小裁判主板和装甲板子板归本任务处理。
2. 车端只作为对接对象，不改车端控制逻辑。
3. 车端是否直接读取 `0x0206 hurt_status` 不阻塞本阶段；小裁判主板仍会发送 `0x0206`，并同步 `0x0201.current_hp`。

## 裁判协议最小闭环

裁判串口帧格式：

```text
frame_header(5) + cmd_id(2) + data(n) + frame_tail(2)
```

帧头字段：

```text
SOF = 0xA5
data_length = data 段长度，小端
seq = 包序号
CRC8 = 帧头 CRC8
```

帧尾为整包 `CRC16`，小端。

最小闭环需要周期发送保活 / 状态帧，并在受击时立即发送受击帧：

| cmd_id | 名称 | 频率 / 时机 | 作用 |
|---|---|---|---|
| `0x0201` | `robot_status` | `10Hz` | 本车 ID、等级、当前血量、血量上限、功率上限、电源输出状态 |
| `0x0206` | `hurt_status` | 受击后立即发送 | 告诉车端哪块装甲、什么原因导致扣血 |
| `0x0003` | `robot_hp` | `3Hz` | 同步己方机器人血量表 |
| `0x0202` | `power_heat_data` | `10Hz` | 缓冲能量和射击热量；小闭环可先填默认值 |
| `0x0208` | `allowed_bullet` | `10Hz` | 允许发弹量；小闭环可先填默认值 |
| `0x0001` | `game_status` | `1Hz` | 比赛类型、阶段、剩余时间 |

`0x0208` 在 PDF 概览表写 6 字节，但详细字段和当前车端代码都是 8 字节，后续按 8 字节处理。

### 受击帧 `0x0206`

数据长度：`1 byte`

```c
typedef struct __attribute__((packed))
{
    uint8_t armor_id  : 4;
    uint8_t hurt_type : 4;
} hurt_status_t;
```

组包方式：

```text
payload[0] = (hurt_type << 4) | armor_id
```

常用 `hurt_type`：

```text
0 = 装甲模块被弹丸攻击导致扣血
1 = 装甲模块或超级电容管理模块离线导致扣血
5 = 装甲模块受到撞击导致扣血
```

本任务最小闭环优先使用：

```text
hurt_type = 0
armor_id = 0 / 1 / 2 / 3
```

#### 第一轮 CubeMX 操作建议

为避免一次性关闭太多外设导致编译问题，第一轮只做“硬件 profile 对齐”，步骤如下：

1. 保持 `ProjectManager.TargetToolchain = CMake`、`SYS > Debug = Serial Wire`、`RCC > HSE`、`HAL Timebase = TIM1`。
2. 复核时钟树为 `HSE 8MHz -> PLL x9 -> SYSCLK 72MHz`、`APB1 36MHz`、`APB2 72MHz`。
3. 把 `UART4` 从 `100000 / 9B / Even` 改为 `115200 / 8N1 / No parity`。
4. 新增 `UART5 PC12_TX / PD2_RX`，配置为 `115200 / 8N1 / No parity`。
5. 在 `UART5 > NVIC Settings` 中勾选 `UART5 global interrupt`。如果后续使用 `ReceiveToIdle`、中断接收或 DMA + IDLE，UART 全局中断必须打开，否则 IDLE 事件不会进入 HAL 回调。
6. 配置 `PB0 / PB1 / PB2` 为 `GPIO_Output`，用于 RGB 状态灯。输出模式建议 `Output Push Pull`、初始 `Low`、`Low Speed`；`GPIO Pull-up/Pull-down` 可设为 `No pull`，不必开内部上拉。
7. 配置 `PC6 / PC7` 为 `GPIO_Input + Pull-Up`，释放前先关闭对应 `TIM3_CH1 / TIM3_CH2`。
8. 若确定 `PA11 / PA12` 要做 `SW3 / SW4`，先在 CubeMX 中释放 `CAN1` 引脚；生成代码后立刻检查 CAN 相关编译影响。
9. 若 OLED 实物接 `PB8 / PB9`，把 `I2C1` remap 到 `PB8 / PB9`，但模式必须选择普通 `I2C`，不要选择 `SMBus-Alert-mode`。普通 OLED 只需要 `PB8 = I2C1_SCL`、`PB9 = I2C1_SDA`，不需要 `PB5 = I2C1_SMBA`。
10. 生成代码后不要立刻写业务，先执行一次 CMake configure/build，确认 CubeMX 生成代码和 BSP 仍能编译。

#### CubeMX 截图复核注意

根据 2026-07-25 的 CubeMX 配置截图，补充以下判断：

1. `PA11 / PA12 / PC6 / PC7` 配成 `Input mode + Pull-up` 是合理的，适合作为板载开关输入。
2. `PB0 / PB1 / PB2` 配成 `Output Push Pull + Low Speed + 初始 Low` 是合理的；内部 `Pull-up` 对推挽输出没有必要，建议改成 `No pull`，除非实测 LED 电路需要上拉。
3. `UART5 global interrupt` 当前截图未勾选，应勾选。装甲板串口后续大概率使用 `ReceiveToIdle`，没有 UART 全局中断会导致 IDLE 回调不可靠或不触发。
4. `I2C1` 当前截图显示为 `SMBus-Alert-mode`，这是不合适的。OLED 应使用普通 `I2C` 模式，且不需要 `PB5/I2C1_SMBA`。

## 装甲板子板 CubeMX 配置

目标芯片：`STM32G030F6P6`。子板原理图未见外部 HSE，使用内部时钟。

### 子板固定外设

| 功能 | CubeMX 外设 / 管脚 | 参数 |
|---|---|---|
| 系统时钟 | `HSI16` 或 `HSI16 + PLL = 64MHz` | 不使用外部 HSE |
| 调试 | `Serial Wire` | `PA13 SWDIO / PA14 SWCLK` |
| 子板通信 | `USART2 PA2_TX / PA3_RX` | `115200 8N1` |
| 模拟受击 | `PA0 ADC_IN0` | 12bit，右对齐 |
| 数字触发 | `PA1 DX` | 先配 `GPIO_Input`，确认高 / 低有效后再决定 EXTI |
| 装甲灯 | `PA4 LED_B / PA5 LED_R` | 先普通 `GPIO_Output`，PWM 属升级项 |

`U5` 是外接检测模块 4P 接口：

| U5 引脚 | 网络 | 判断 |
|---:|---|---|
| 1 | `GND` | 外接模块地 |
| 2 | `+5V` | 外接模块供电 |
| 3 | `AX` | 模拟输出，进入 `PA0 ADC_IN0` |
| 4 | `DX` | 数字触发输出，进入 `PA1` |

子板第一版只做三件事：

1. 周期上报 `AX` 的 ADC 原始值。
2. 周期上报 `DX` 的实时电平。
3. 当 `DX` 触发或 `AX` 超阈值时，上报一次受击事件。

子板符号库里存在 `PB7/PB8`、`PB3/PB4/PB5/PB6` 这类复合脚名，实际 CubeMX 配置时要以 `STM32G030F6P6` 封装脚位为准。

### 子板上报协议 V0.1

子板到主控板的第一版协议不直接使用 RoboMaster 裁判帧，先用自定义小包降低调试难度；主控板收到后再转换成 `0x0206 hurt_status` 和 `0x0201 robot_status`。

```text
SOF(1) + armor_id(1) + event(1) + dx(1) + ax_raw(2) + seq(1) + sum8(1)
```

| 字段 | 建议值 / 含义 |
|---|---|
| `SOF` | 固定 `0xA5`，方便串口抓包 |
| `armor_id` | 固件默认 `0~3`，单板调试时可先全填 `0` |
| `event` | `0 = heartbeat`，`1 = hit_dx`，`2 = hit_adc`，`3 = hit_both` |
| `dx` | 当前 `DX` 电平，`0 / 1` |
| `ax_raw` | `ADC1 PA0` 原始值，小端 |
| `seq` | 子板自增序号 |
| `sum8` | 前面所有字节累加取低 8 位 |

第一版发送频率：

| 包类型 | 频率 / 时机 | 用途 |
|---|---|---|
| 心跳包 | `20Hz` | 主控判断子板在线、记录 `AX/DX` |
| 受击包 | 触发后立即发 `3` 次，间隔 `5ms` | 降低串口丢包影响 |
| 调试包 | 可与心跳共用 | 串口助手观察原始值 |

### 子板受击判定 V0.1

先用“数字触发优先，模拟阈值辅助”的策略：

1. 上电前 `500ms` 不判定受击，只采集基线。
2. `AX` 基线取最近 `64` 次采样平均值。
3. `DX` 触发边沿由实测决定，初版先支持编译宏切换：
   - `ARMOR_DX_ACTIVE_HIGH = 1`
   - `ARMOR_DX_ACTIVE_HIGH = 0`
4. `AX` 判定条件先用 `ax_raw > ax_baseline + ax_threshold`。
5. 触发一次受击后进入 `100ms` 冷却，冷却期内不重复上报。
6. 每次触发记录 `last_hit_source`，用于区分 `hit_dx / hit_adc / hit_both`。

初始参数建议：

| 参数 | 初始值 | 说明 |
|---|---:|---|
| `ax_sample_hz` | `1000Hz` | 定时采样 |
| `heartbeat_hz` | `20Hz` | 子板在线状态 |
| `hit_cooldown_ms` | `100ms` | 防抖 / 防连发 |
| `ax_threshold` | 待实测 | 先通过串口打印标定 |
| `dx_active_level` | 待实测 | 由上电实测项决定 |

### 软件计划变更：接入 `mas_embedded_threadx`

主控板软件计划已变更：**不再使用 Keil 简单裸 HAL 工程**，而是基于已经开发好的 CMake + ThreadX 完整工程继续做小裁判主控业务：

```text
D:\Code_for_Keil5\HAL\mas_embedded_threadx
```

CubeMX 仍然使用，但角色变成“生成板级 HAL / 启动文件 / 链接脚本 / 外设初始化”的来源；业务代码进入 `apps` / `modules` / `board` 体系。

当前工程已有基础接入结构：

```text
mas_embedded_threadx
├── board/
│   └── 105_rc/                       # 已有 F105 主控板 BSP，来源于 CubeMX
├── apps/
│   ├── test/                          # 原有测试业务，可作为参考，不再作为小裁判长期业务线
```

业务线已确定为新建 `ROBOT=referee_main`、`BOARD=single`。`apps/test/single_board` 只作为 ThreadX 线程创建、日志和 UART 调试写法的参考，不再承载小裁判主控长期代码。

这样做的原因：

1. 小裁判主控不是普通机器人控制板，长期占用 `test` 会让配置和业务含义混乱。
2. 新业务线可以独立维护 `robot.cmake`、模块开关、线程优先级和默认裁判状态。
3. 每次新增功能都能以独立 commit 落在清晰路径下，方便回溯。
4. 后续如果需要同时保留 `test` 和 `referee_main`，两者不会互相污染。

### 2. 主控板最小初始化

先只保留最短路径，确认板子能稳定跑：

```c
HAL_Init();
SystemClock_Config();

MX_GPIO_Init();
MX_I2C1_Init();
MX_USART1_UART_Init();

tx_kernel_enter();
```

实际工程里不需要在业务文件中手写上述入口；这里只表达最小初始化链路。`105_rc` 工程由启动文件 / `main.c` / ThreadX 入口进入 `Robot_Init()`，再通过 `APP_Init()` 创建小裁判业务线程。

第一阶段验证：

1. `PB0/PB1/PB2` 能正常闪灯，并记录 LED 高 / 低电平点亮关系。
2. `I2C1` 能扫到 OLED 地址，常见为 `0x3C` 或 `0x3D`，以实物为准。
3. `USART1` 能用串口工具看到输出。
4. 用 `USART1` 周期发送合法 `0x0201 robot_status`，车端 `USART6` 接收后不离线。
5. 加入 `0x0001 / 0x0003 / 0x0202 / 0x0208` 周期帧。
6. 手动触发一次 `0x0206 hurt_status`，确认受击事件或血量状态同步正常。

### 3. 接入四路装甲板

主控板裁判输出稳定后，再打开四路装甲板串口：

1. 先开 `USART2`，只接一块装甲板，验证子板上报数据。
2. 再按顺序打开 `USART3 / UART4 / UART5`。
3. 每块装甲板固定一个 `armor_id`，初始建议：
   - `USART2 -> armor_id 0`
   - `USART3 -> armor_id 1`
   - `UART4 -> armor_id 2`
   - `UART5 -> armor_id 3`
4. 主控板收到任意子板受击事件后：
   - 记录 `armor_id`
   - 扣减本地 `current_hp`
   - 立即发送 `0x0206 hurt_status`
   - 下一轮 `0x0201 robot_status` 同步新的 `current_hp`

### 4. 新建装甲板子板工程

1. CubeMX 新建 `STM32G030F6P6` 工程。
2. 开启 `SYS > Debug = Serial Wire`。
3. 使用内部时钟，先用 `HSI16` 即可；若需要余量再配到 `64MHz`。
4. 开启 `USART2 PA2_TX / PA3_RX`，`115200 8N1`。
5. 开启 `ADC1 PA0`，采集 `AX`。
6. 开启 `PA1` 输入，读取 `DX`。
7. 开启 `PA4 / PA5` 普通输出，控制红 / 蓝装甲灯。
8. 固件先持续上报 `AX` 原始值和 `DX` 电平，用于标定。

### 5. 上电调试顺序

1. 单独给小裁判主板上电，确认 `3.3V`、`5V`、`24V_LOAD` 无异常发热。
2. 连接 ST-Link，确认 SWD 能下载和复位。
3. 跑 LED 闪烁程序，确认 `PB0/PB1/PB2` 点亮电平。
4. 跑 I2C 扫描，确认 OLED 地址。
5. 跑 `USART1` 裁判帧发送，确认车端 `USART6` 收包。
6. 单独调一块装甲板，记录 `AX` 空闲值、受击峰值、`DX` 触发电平。
7. 接入四块装甲板，逐块确认 `armor_id` 与物理位置对应关系。
8. 跑完整闭环：敲击装甲板 -> 子板上报 -> 主控扣血 -> `USART1` 发 `0x0206` 和更新后的 `0x0201`。

### 闭环验收标准

第一版闭环完成的定义：

1. `board/105_rc` 能通过 CMake 配置和编译。
2. ThreadX 能在 `STM32F105RCT6` 上启动，并进入小裁判业务线程。
3. 小裁判主板单独上电稳定，`3.3V / 5V / 5V_LOAD` 正常。
4. 主控板 `USART1` 周期发 `0x0201` 后，车端 `REFEREE` 不离线。
5. 主控板继续加入 `0x0001 / 0x0003 / 0x0202 / 0x0208` 后，车端状态仍稳定。
6. 单块装甲子板能上报 `AX / DX`，主控能解析。
7. 敲击装甲板后，主控立即发送 `0x0206 hurt_status`。
8. 下一帧 `0x0201 robot_status.current_hp` 已扣血。
9. 四块装甲板分别触发时，`armor_id = 0 / 1 / 2 / 3` 与物理位置一致。
10. 连续敲击时不会因为抖动一次扣多次，冷却时间可配置。

## 后续升级项

### 装甲子板在线 / 离线模式约定 V0.2

装甲子板上电默认进入离线模式。只有收到主控发送的合法配置 / 保活帧后，才进入在线模式；不能因为收到单个字节或不完整帧而切换在线。

主控到装甲子板的配置 / 保活帧固定为 8 字节：

```text
0xA5 + 0xC1 + team + armor_id + mode + flags + seq + sum8
```

字段约定：

| 字节 | 字段 | 含义 |
|---:|---|---|
| 0 | `SOF` | 固定 `0xA5` |
| 1 | `cmd` | 固定 `0xC1`，表示装甲子板配置 / 保活 |
| 2 | `team` | `0` 红方，`1` 蓝方 |
| 3 | `armor_id` | 装甲位置编号，通常为 `0~3` |
| 4 | `mode` | `1` 表示在线配置 / 保活 |
| 5 | `flags` | 预留，当前填 `0` |
| 6 | `seq` | 主控自增序号 |
| 7 | `sum8` | 前 7 字节累加后取低 8 位 |

主控应周期发送该帧，建议频率为 `10Hz`。子板收到完整且校验正确的帧后，更新 `team`、`armor_id` 和最后接收时间，并进入在线模式。超过 `500ms` 没有收到合法配置 / 保活帧时，子板先执行离线提示：红、蓝交替闪烁 3 轮，共 6 个半周期，每半周期 `100ms`；提示结束后才切换为离线模式。

在线模式下：

- 本地红蓝按键无效；阵营和 `armor_id` 由主控配置帧决定。
- 红方空闲亮红灯，受击亮蓝灯。
- 蓝方空闲亮蓝灯，受击亮红灯。

离线模式下使用装甲子板上的两个硬件按键：

- `KEY_1 / PB6`：红方选择。
- `KEY_2 / PB7`：蓝方选择。
- 按键为低电平按下，硬件默认上拉；软件做约 `20ms` 消抖。
- 只有一个按键按下时切换阵营；两个同时按下时不切换。
- 离线模式下按键可随时切换颜色，切换后按当前阵营显示空闲色；受击颜色为当前阵营的反色。

离线模式仍保留装甲子板自身的 AX / DX 采样、受击判定和子板状态上报；在线 / 离线状态只决定阵营来源和 LED 显示控制权。

最小闭环跑通后再考虑：

1. 四路装甲板 UART 改为 `DMA Circular + IDLE` 接收。
2. 装甲板 `LED_R / LED_B` 从 GPIO 改 PWM 调光。
3. OLED 显示血量、装甲板在线状态、最近受击位置。
4. 参数保存：血量、阈值、`armor_id` 映射、触发电平。
5. 更完整的掉线检测和异常保护。
6. 车端如需直接读取 `0x0206`，再另开车端模块修改任务。
